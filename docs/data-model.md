# โครงสร้างข้อมูลข้อความ LINE

สถานะ: มี migration, backend รับข้อความ และการทดสอบ SQLite ในเครื่องแล้ว ยังไม่ได้สร้างหรือแก้ฐานข้อมูล Cloudflare จริง

## ข้อกำหนดข้อมูลที่ยืนยัน

| ข้อมูล | ชื่อฟิลด์ | ความหมาย |
| --- | --- | --- |
| รหัสกลุ่ม | group_id | รหัสกลุ่มจาก LINE ไม่ใช้ชื่อกลุ่มเป็นกุญแจ |
| รหัสข้อความ | message_id | รหัสข้อความจาก LINE เก็บเป็นข้อความเพื่อไม่เสียความแม่นยำ |
| รหัสผู้ส่ง | sender_id | รหัสผู้ส่งจาก LINE หากไม่มีให้เป็น NULL |
| ชื่อผู้ส่ง | sender_display_name | ชื่อที่ทราบตอนรับข้อความ ไม่เขียนทับประวัติเมื่อเปลี่ยนชื่อ หากไม่มีให้เป็น NULL และแสดงว่าไม่ทราบผู้ส่ง |
| เวลาส่ง | sent_at_ms | UTC Unix milliseconds จาก LINE เก็บเป็นค่าหลัก |
| เวลาส่งแบบไทย | sent_at_thai | ค่าแสดงผล ISO 8601 พร้อม +07:00 จาก view |
| เขตเวลา | timezone | Asia/Bangkok จาก view |
| เนื้อหาเดิม | original_text | ข้อความตอนส่งครั้งแรก |
| เนื้อหาล่าสุด | current_text | ฉบับแก้ไขล่าสุดจาก view หรือข้อความเดิมหากไม่เคยแก้ไข |
| ข้อความที่ตอบกลับ | replied_to_message_id | รับจาก LINE quotedMessageId เฉพาะเมื่อมี ไม่เดาจากลำดับแชท |
| สถานะ | message_status | active, edited หรือ unsent จากประวัติ |
| เวลาแก้ไข/ยกเลิกส่ง | edited_at_ms, unsent_at_ms | เวลาเหตุการณ์จาก LINE; NULL หากไม่เคยเกิด |
| จำนวนฉบับ | version_count | ต้นฉบับหนึ่งฉบับบวกจำนวนเหตุการณ์แก้ไขที่ไม่ซ้ำ |

ไม่บังคับ foreign key สำหรับข้อความที่ตอบกลับ เพราะอาจอ้างถึงข้อความก่อนบอตเข้ากลุ่มหรือข้อความที่ลบตามอายุแล้ว

## ตารางและมุมมอง

- `messages`: หนึ่งแถวต่อคู่ group_id + message_id เก็บตัวตนผู้ส่ง เวลา และข้อความเดิม
- `message_events`: เหตุการณ์ received, edited, unsent ใช้ webhook_event_id เป็นกุญแจกัน webhook ซ้ำ เก็บข้อความฉบับนั้นใน received/edited ส่วน unsent เก็บ text เป็น NULL โดยไม่ลบข้อความในต้นฉบับหรือฉบับแก้ไข
- `message_current`: หนึ่งแถวต่อข้อความพร้อมข้อความล่าสุด สถานะ และเวลาไทย แม้แก้ไขหลายครั้งก็ไม่เพิ่มจำนวนข้อความหลัก
- `ai_messages`: หนึ่งแถวต่อข้อความ ใช้ฉบับล่าสุดและตัดรายการยกเลิกส่งออกจากการนับ/สรุปบทสนทนาปัจจุบันโดยปริยาย หากต้องวิเคราะห์ประวัติหรือข้อความยกเลิกส่ง ต้องเลือก `message_current` หรือ `message_history` อย่างชัดเจน
- `message_history`: ทุกเหตุการณ์และทุกฉบับสำหรับตรวจย้อนหลัง ไม่ใช้ COUNT(*) จากมุมมองนี้เป็นจำนวนข้อความสนทนา

ตัวอย่าง: ส่ง “นัด 9 โมง” แล้วแก้เป็น “นัด 10 โมง” จะมีหนึ่งข้อความใน ai_messages พร้อม current_text = “นัด 10 โมง” และ version_count = 2 เมื่อยกเลิกส่ง message_current ยังเก็บเนื้อหาและเปลี่ยนสถานะเป็น unsent แต่ ai_messages ไม่รวมในการนับบทสนทนาปัจจุบัน

## กติกาของ backend

1. ตรวจลายเซ็น LINE ก่อนบันทึกข้อมูล ใช้ parameter binding ทุกครั้ง
2. รับข้อความใหม่: เพิ่ม messages และ received event ใน D1 batch เดียวกัน ใช้ ON CONFLICT DO NOTHING กับกุญแจที่กำหนดเพื่อรับ webhook ซ้ำได้
3. รับการแก้ไขหรือยกเลิกส่ง: เพิ่ม message_events โดยไม่แก้เวลาส่งเดิม ไม่ลบต้นฉบับ และไม่สร้างข้อความหลักเพิ่ม
4. เหตุการณ์อาจมาผิดลำดับ จึงไม่บังคับ FK จาก events ไป messages: เก็บเหตุการณ์ที่มาก่อนต้นฉบับไว้ก่อน เมื่อมีต้นฉบับ view จะประกอบสถานะให้เอง ถ้าต้นฉบับไม่เคยมาถึงให้แสดงเป็นรายการไม่สมบูรณ์ในหน้าจัดการ ไม่สร้างเนื้อหาหรือเวลาส่งขึ้นเอง
5. ใช้ event_at_ms เลือกฉบับแก้ไขล่าสุด ไม่ใช้เวลาที่เซิร์ฟเวอร์รับ ถ้าเวลาเท่ากันใช้ event ID เป็นลำดับคงที่ ซึ่งไม่ได้รับรองลำดับการกระทำที่แท้จริงภายใน millisecond เดียวกัน
6. ส่งข้อมูลลง Sheets ทันที โดยแท็บหลักมีหนึ่งแถวต่อข้อความ อัปเดตสถานะ/ฉบับล่าสุดในแถวเดิม เก็บประวัติทุกเหตุการณ์ในส่วนประวัติแยก และอย่านับประวัติเป็นข้อความใหม่
7. ตั้ง sheets_synced_at_ms หลังยืนยันการส่งครบทั้งข้อความปัจจุบันและประวัติแล้วเท่านั้น ความเป็น atomic ระหว่าง D1 กับ Sheets ต้องทำด้วย checkpoint/การเขียนซ้ำที่ให้ผลเดิมใน backend; schema เพียงอย่างเดียวยังไม่รับรอง exactly-once
8. การกันส่งซ้ำฝั่ง Sheets ต้องใช้รหัสข้อความ/เหตุการณ์เป็นตัวอ้างอิง ไม่ใช้ชื่อผู้ส่งหรือข้อความเนื้อหา

## อายุข้อมูลและแผนฟรี

Google Sheets เป็นที่เก็บประวัติหนึ่งปีตามแบบเดิม D1 เก็บ cache 7 วันและรายการยังไม่สำเร็จสำหรับส่งซ้ำ/กู้คืน ไม่ได้พักเพื่อรอรอบรายวัน มี maintenance แบบทยอยล้างเฉพาะรายการที่ส่งสำเร็จแล้ว และเก็บพิกัดของรายการส่งไม่สำเร็จไว้ การล้างประวัติบนชีตใช้การเคลียร์ค่าโดยไม่เลื่อนแถวและย้ายไฟล์เดือนที่หมดอายุทั้งเดือนไปถังขยะ

แบบปัจจุบันยังไม่ผ่านเป้าฟรีที่ 10,000 ข้อความ/วัน เนื่องจากมีหลายการเขียนและดัชนีต่อข้อความ รวมการล้าง cache ไม่ควรอ้างว่าการทดสอบ SQLite ในเครื่องรับรองโควตา Cloudflare จริง ดูข้อจำกัดใน README

เมื่อล้าง cache แล้ว view ใน D1 ครอบคลุมเฉพาะข้อมูลที่ยังอยู่ใน cache การวิเคราะห์ระยะยาวต้องอ่านชีตหลักและประวัติใน Sheets ส่วน backend ใช้ชีตเดิมเป็นฐานเมื่อได้รับการแก้ไขที่อยู่นอก cache

## การตรวจสอบ

รัน `python -m unittest discover -s tests -v` เพื่อตรวจ SQL กับ SQLite ในเครื่อง ครอบคลุมเวลาไทยข้ามวัน ข้อความตอบกลับที่ไม่อยู่ในฐานข้อมูล ผู้ส่งที่ขาดข้อมูล เหตุการณ์แก้ไขมาผิดลำดับ การส่งซ้ำ และสถานะแก้ไขร่วมกับยกเลิกส่ง ยังไม่ใช่การทดสอบบน Cloudflare จริง
